## Business rules

1. Address create/edit/select/delete and bulk delete operate only on caller-owned IDs. Bulk unauthorized IDs roll back the entire operation; selected-address changes are serialized so one address is selected at most.
2. addFavourite toggles the existing relationship according to actual client contract; use unique(customerId,restaurantId), deterministic concurrency semantics and active restaurant validation. userFavourite returns only caller records.
3. Customer/admin list detail, ordersByUser, notes and status changes enforce reference/04 role permission and tenant restrictions. Return public profile fields only; no password hash, tokens, reset proof or internal privileged notes.
4. Suspension/deletion communicates with L1 session revocation via transaction/outbox; historical orders and finance evidence survive deletion with policy-approved redaction. No arbitrary mass cascading erase.
5. Support ticket/message reads and writes enforce participant ownership; admin support permission permits service handling. Author identity is server-derived. Enforce bounded text and transition matrix, optimistic version and audit trail; reject messages to closed ticket unless the verified source flow explicitly reopens it.
6. Support timestamps use epoch-millisecond strings. Retry-safe message creation records stable request identity where supported; websocket/push effects go through L8 port and durable outbox after commit.

Client auth errors preserve `UNAUTHENTICATED`, `TOKEN_EXPIRED`, `INVALID_TOKEN`, `FORBIDDEN`; use the master error table. Invalid business inputs use `BAD_USER_INPUT`; missing/unseen entities use `NOT_FOUND`; concurrent state/version conflicts use `CONFLICT`. Unimplemented capability returns `NOT_IMPLEMENTED`. Unconfigured provider returns `PROVIDER_UNAVAILABLE`; unavailable infrastructure must fail visibly. Business error messages must avoid token-retry trigger phrases. Any inferred policy not established in references must be recorded as UNVERIFIED and independently reviewed before release.

Each task below is independently tracked. Write the named tagged integration suite first, run it and record failure, implement the service/repository/resolver path, then rerun to green and commit `feat(LANE): implement ROOT`. Common cases in every task: assert the exact selected business fields, `__typename`, IDs and wire timestamps/amounts; invalid required input and boundary limits; missing token for protected roots; expired/revoked token and wrong role; substituted foreign tenant/customer/restaurant IDs; no database change or event on rejection. Public roots instead prove intentional public access plus safe field projection, missing public handshake denial, abuse limits and malformed inputs. Scalar/no-ID roots record why ownership substitution is inapplicable and test recipient/session binding instead. Mutation tasks also run parallel conflicting requests, duplicate/replay input and transaction failure, checking unique constraints, optimistic conflict behavior and atomic outbox. Read tasks run pagination/filter isolation, inactive/deleted visibility and concurrent update/read consistency.

Worker file changes outside this lane require lead/owning-lane integration.
