## Business rules

1. Authenticate each customer, rider, restaurant and owner against the correct principal kind; disabled principals never acquire a usable session. Preserve ownerLogin → ownerSession → refreshToken transport contract.
2. Derive emailIsVerified/phoneIsVerified from consumed server challenges; never trust client flags. Invalid verifyOtp throws BAD_USER_INPUT because several clients test object truthiness.
3. OTP challenges bind purpose and recipient, expire, cap attempts and enforce resend limits; concurrent verify attempts consume exactly one challenge. A password reset requires a consumed reset challenge or signed one-time proof, never email alone.
4. Refresh rotation is transactional; concurrent reuse revokes the family. Deactivate, changePassword, resetUserSession and deleteStaff revoke affected HTTP and WS sessions.
5. Google/Apple login verifies signature, issuer, audience and nonce with provider keys; unconfigured provider fails PROVIDER_UNAVAILABLE. Apple nonce is single-use; never accept bare appleId.
6. Notification tokens are opaque registered destinations scoped to authenticated principal, platform and consent; tokens and hashes are redacted in logs and unauthorized fields.

Client auth errors preserve `UNAUTHENTICATED`, `TOKEN_EXPIRED`, `INVALID_TOKEN`, `FORBIDDEN`; use the master error table. Invalid business inputs use `BAD_USER_INPUT`; missing/unseen entities use `NOT_FOUND`; concurrent state/version conflicts use `CONFLICT`. Unimplemented capability returns `NOT_IMPLEMENTED`. Unconfigured provider returns `PROVIDER_UNAVAILABLE`; unavailable infrastructure must fail visibly. Business error messages must avoid token-retry trigger phrases. Any inferred policy not established in references must be recorded as UNVERIFIED and independently reviewed before release.
